# RICK Intelligence system architecture

Status: `PHASE 2 / LOCAL IMPLEMENTATION IN PROGRESS`.

RICK is a knowledge, reasoning, evidence and verification platform. The API is
the composition boundary; it does not own durable data or invent a second
implementation of a preserved system.

```text
identity + authorization + audit + policy
                 │
                 ▼
        ┌──────────────────┐
        │ canonical API     │
        └───────┬──────────┘
                │
      ┌─────────┼─────────┐
      ▼         ▼         ▼
 knowledge   reasoning  control
 plane       plane      plane
      │         │         │
      └────┬────┴────┬────┘
           ▼         ▼
      evidence   verification
           └────┬────┘
                ▼
          decision layer
                ▼
             API / Web
```

The knowledge plane owns document lineage, parsing, chunking, embeddings,
vector indexing and authorization-aware retrieval. The reasoning plane owns
provider-neutral Professor orchestration and bounded tool use. The control
plane owns identity, authorization, tenant scope, audit, lifecycle gates and
operational policy. Evidence is generated by the server and is the only source
material allowed to reach grounded generation.

The dependency direction is `apps -> packages -> shared contracts`. Packages do
not import application or preserved legacy paths. The three preserved systems
remain compatibility and migration surfaces. A caller migration must pass
through an explicit contract, adapter, differential verification and an
approved production gate before removal is considered.

The current local implementation contains the durable job contract, a scoped
PostgreSQL queue adapter, a bounded worker runtime, typed object/vector/provider
ports, evidence-gated Professor behavior, tenant-aware retrieval and a
production composition hook. The external PostgreSQL, Redis, Qdrant, object
store, provider, deployment and multi-process gates are recorded separately;
their absence is never represented as readiness.

## Request and execution flow

1. Middleware derives request and correlation identifiers, trusted client
   address, CSRF/origin policy and bounded body limits.
2. Identity and authorization create a server-owned tenant/workspace scope.
3. Retrieval applies tenant, workspace and collection filters before and after
   the backend call, then emits bounded provenance.
4. Professor accepts only scoped evidence, binds citations to server-generated
   evidence IDs and maps failures to safe outcomes.
5. Durable ingestion writes immutable source content, enqueues a scoped job and
   lets a worker advance the state machine. Publication occurs only after
   verification.
6. Audit and telemetry receive redacted, bounded observations outside the
   authoritative transaction.

## Ownership boundaries

| Boundary | Owner | Required invariant |
| --- | --- | --- |
| tenant/workspace/collection | identity + authorization | every read and write has server-derived scope |
| job state and lease | durable queue | owner and version fence every mutation |
| source bytes | object store | checksum, immutable key and bounded stream |
| vector read model | Qdrant adapter | ACL filter plus response revalidation |
| generated answer | Professor/provider | no generation without approved evidence |
| decision | decision layer | explicit answer/retrieve/clarify/abstain/escalate outcome |
| audit/telemetry | redaction-aware sinks | no secrets, raw content or unbounded labels |
